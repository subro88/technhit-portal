## Key Architecture Takeaways

- **Eliminate Split-Brain with Dual-Ring Corosync**: Deploying dual redundant Totem communication rings across independent physical network interfaces guarantees that transient link degradation cannot trigger dual-primary state divergence.
- **Shared-Nothing Synchronous Storage (DRBD 9 Protocol C)**: Replicating database block devices over a dedicated point-to-point link with synchronous write barriers ensures 0-byte transaction data loss across primary node crashes.
- **Strict Node Fencing via STONITH**: Operating an active-passive stateful database cluster without Shoot The Other Node In The Head (STONITH) guarantees data corruption; Pacemaker must physically reset partitioned nodes via Proxmox PVE API or IPMI BMC before promoting secondary storage.
- **Colocation & Ordered Resource Orchestration**: Pacemaker resource sets enforce atomic dependency bindings: the Virtual IP (`10.10.10.100`), DRBD primary promotion, `/var/lib/mysql` filesystem mount, and `mysqld` service must always bind to the same voting node in strict sequential order.

## High-Availability Active-Passive Failover Architecture

In production database environments running bare-metal servers or private KVM/Proxmox hypervisors, single-node hardware failures—such as power supply blowouts, kernel panics, or memory bus errors—can lead to catastrophic unplanned downtime. 

While active-active multi-master systems (like MySQL Galera or NDB Cluster) introduce complex write latency penalties and distributed locking overhead, an **Active-Passive High-Availability Cluster** using **Corosync**, **Pacemaker**, and **DRBD 9** delivers maximum single-thread write throughput with instantaneous, automated failover.

## The Three Core Pillars of Active-Passive Linux Clustering

### 1. Heartbeat Redundancy & Split-Brain Prevention (Corosync 3)

Corosync is the cluster messaging and membership layer. It maintains the **Totem Single Ring / Multiple Ring Redundant Protocol**, passing heartbeat tokens continuously between cluster members.

If a network switch fails and the nodes cannot see each other, each node might assume the other is dead and attempt to promote its local storage. This is known as **Split-Brain Syndrome**. If both nodes become primary and write to their local copies of the database simultaneously, the filesystem and InnoDB tablespaces suffer unrecoverable divergence.

To prevent split-brain:
1. **Redundant Dual-Ring Topology**: Corosync 3 uses Kronosnet (knet) to transport heartbeat tokens across two completely separate physical networks simultaneously:
   - **Ring 0 (Management / Ingress)**: `10.10.10.0/24` via top-of-rack switches.
   - **Ring 1 (Private Heartbeat / Storage Crossover)**: `10.20.20.0/24` via direct point-to-point 10GbE DAC/SFP+ cabling.
2. **Quorum Device (QDevice / QNetd)**: In a 2-node cluster, 1 node failure leaves the remaining node with only 50% of the vote (no majority). A lightweight external witness daemon (`corosync-qdevice` on a separate Raspberry Pi or cloud VM) acts as the tiebreaker, providing the 3rd vote needed to form legal quorum.

### 2. Shared-Nothing Block Storage (DRBD 9 Protocol C)

Traditional clustering relied on costly shared SAN/NAS arrays (iSCSI, Fibre Channel), which themselves introduced a single storage controller point of failure. **DRBD (Distributed Replicated Block Device)** operates as a Linux kernel driver that mirrors block devices (`/dev/drbd0`) over high-speed networks, creating virtual shared storage with zero shared hardware.

DRBD operates in three distinct replication modes:
- **Protocol A (Asynchronous)**: Writes are acknowledged locally as soon as they hit local disk and the TCP send queue. Fast over high-latency WANs, but risks data loss on sudden power failure.
- **Protocol B (Memory Synchronous)**: Writes are acknowledged once received in peer RAM buffer.
- **Protocol C (Synchronous)**: Writes are only acknowledged to the application (MySQL) when written to **both** local persistent storage and peer remote storage. **This is mandatory for high-availability database clusters.**

### 3. Absolute Node Isolation (STONITH Fencing)

In high-availability clustering, **fencing** is the non-negotiable mechanism that isolates an unresponsive node. 

> **Cluster Golden Rule**: A node must never be assumed dead; it must be confirmed dead.

If `db-node-01` experiences a temporary 10-second kernel CPU lockup or high load spike, it might drop Corosync heartbeats. If `db-node-02` blindly promoted itself while `db-node-01` was still flushing dirty pages to the block device, catastrophic data destruction occurs.

**STONITH (Shoot The Other Node In The Head)** ensures that before `db-node-02` can promote DRBD or bind the Virtual IP, it issues a hardware command (via IPMI/iLO/iDRAC BMC or Proxmox VE API `fence_pve`) to forcibly yank power from `db-node-01` or issue an immediate hardware reboot. Only after receiving hardware attestation that `db-node-01` is dead will Pacemaker complete the failover.

    <CodeTabs>

```
    protocol C;

    net {
        cram-hmac-alg sha256;
        shared-secret "TechNHIT-Cluster-Drbd-Secret-Key-2026";
        max-epoch-size 8000;
        max-buffers 8000;
        sndbuf-size 2M;
        rcvbuf-size 2M;
        after-sb-0pri discard-zero-changes;
        after-sb-1pri discard-secondary;
        after-sb-2pri disconnect;
    }

    disk {
        on-io-error detach;
        fencing resource-and-stonith;
        al-extents 3389;
    }

    on db-node-01 {
        device /dev/drbd0;
        disk /dev/vg_data/lv_mysql;
        address 10.20.20.11:7788;
        meta-disk internal;
    }

    on db-node-02 {
        device /dev/drbd0;
        disk /dev/vg_data/lv_mysql;
        address 10.20.20.12:7788;
        meta-disk internal;
    }
}
```

## Simulated Catastrophic Hardware Failure & Disaster Recovery Drill

To attest that our clustering architecture withstands sudden real-world hardware failures without operator intervention, we execute a destructive failover drill:

### Phase 1: Simulate Sudden Power Loss on `db-node-01`
Trigger an immediate kernel crash / hardware reset on the active node without allowing MySQL to gracefully unmount or flush buffers:

<TerminalBlock
  command="echo c | sudo tee /proc/sysrq-trigger"
  title="Trigger Immediate Kernel Panic on db-node-01"
  os="Linux Kernel"

### Phase 2: Autonomous Cluster Reaction Sequence (Timeline: 8.2 Seconds)
1. **T+0.0s**: Corosync token heartbeat drops on both Ring 0 and Ring 1.
2. **T+1.5s**: Pacemaker on `db-node-02` notices missing heartbeats and queries QDevice witness for quorum consensus.
3. **T+2.2s**: Quorum confirmed. `db-node-02` immediately triggers STONITH fence agent (`fence_pve` / `fence_ipmilan`), commanding the BMC/hypervisor to hard-kill `db-node-01`'s power.
4. **T+3.4s**: STONITH confirms `db-node-01` is severed from the storage fabric.
5. **T+4.1s**: `db-node-02` executes `drbdadm primary r0`, promoting its local block device to Master.
6. **T+5.3s**: Pacemaker mounts `/dev/drbd0` onto `/var/lib/mysql`. Journal recovery runs in milliseconds thanks to synchronous Protocol C writes.
7. **T+6.5s**: Virtual IP `10.10.10.100` binds to `eth0:0` on `db-node-02` and sends Gratuitous ARP packets to the network switch.
8. **T+8.2s**: MySQL systemd service starts. Application database connection pools resume servicing queries with zero data loss.

### Phase 3: Node Re-Integration and Non-Destructive Rejoin
When `db-node-01` reboots, Corosync re-establishes knet heartbeats. DRBD automatically detects that `db-node-02` advanced the generation UUID, attuning `db-node-01` as Secondary and streaming incremental delta blocks to catch up.

## Frequently Asked Questions (AI & Engineering FAQ)

### Why is running a 2-node cluster without STONITH considered dangerous?
Without STONITH fencing, any network glitch or switch reboot severs cluster communication while both physical nodes remain running. Both nodes assume the other is dead and attempt to mount the filesystem and write to MySQL simultaneously. Because DRBD cannot merge divergent block writes, this causes catastrophic **split-brain corruption**, permanently corrupting InnoDB transaction tables.

### What is the difference between DRBD Protocol A, B, and C?
- **Protocol A (Async)**: Write completes locally before peer acknowledges. High throughput across WANs, but data loss occurs on crash.
- **Protocol B (Semi-Sync)**: Write is received in peer network buffers.
- **Protocol C (Sync)**: Write must be committed to physical disk storage on **both** nodes before returning success to MySQL. This provides 100% zero-transaction-loss durability for enterprise databases.

### How does Pacemaker handle Virtual IP (VIP) migration?
Pacemaker utilizes the `IPaddr2` resource agent. When failover occurs, it adds the IP alias (`10.10.10.100`) to the active node's physical network adapter and broadcasts **Gratuitous ARP (GARP)** frames to neighboring top-of-rack switches, instantly updating switch MAC address lookup tables with zero router reconfiguration.
