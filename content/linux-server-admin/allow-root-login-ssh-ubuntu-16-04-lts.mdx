## Key Architecture Takeaways

- **Critical Vulnerability**: Setting `PermitRootLogin yes` with password authentication exposes your server to non-stop automated brute-force botnets targeting port 22.
- **Modern LTS Standard**: Ubuntu 24.04 and 22.04 LTS enforce `PermitRootLogin prohibit-password` by default, strictly disallowing interactive password logins for UID 0.
- **Enterprise Best Practice**: Enforce `PermitRootLogin no`, route all administrative ingress through unprivileged operatives with Ed25519 keys, and mandate auditable `sudo` privilege elevation.
- **Syntax Pre-Flight**: Always validate SSH daemon configuration syntax with `sshd -t` before issuing `systemctl reload ssh` to eliminate lockout risks.

<Callout type="danger" title="Enterprise Security Advisory">
Exposing port 22 with direct root password login enabled is the single most common cause of unauthorized server compromises and botnet infiltration. Production servers must strictly enforce `PermitRootLogin no` or restrict root login exclusively to cryptographic public keys originating from verified bastion CIDRs.
</Callout>

## The Evolution of Root SSH Ingress

In legacy deployments (such as initial installations of Ubuntu 14.04 and 16.04), administrators frequently encountered access denied errors when attempting to connect as `root`. The historical workaround was modifying `/etc/ssh/sshd_config` to `PermitRootLogin yes`.

In modern Linux engineering across **Ubuntu 24.04 LTS (Noble Numbat)**, **Debian 12 (Bookworm)**, and cloud-native server fleets, this practice is strictly prohibited by CIS Linux Benchmarks and NIST compliance frameworks. When root logs in directly, individual operator accountability is lost in `/var/log/auth.log`, and automated dictionary attacks will hammer UID 0 indefinitely.

### Comparing Root Authentication Policies

| Policy Setting | Password Allowed | Key Allowed | Security Posture | Recommended Use Case |
| :--- | :--- | :--- | :--- | :--- |
| `PermitRootLogin yes` | <Badge variant="destructive">Yes</Badge> | Yes | <Badge variant="destructive">Critical Risk</Badge> | Never in production |

## Hardening SSH Ingress: Step-by-Step

<Steps>

### Audit Current OpenSSH Configuration

Query the active operational parameter currently parsed by the running OpenSSH daemon:

```bash
# Check effective PermitRootLogin setting
sudo sshd -T | grep -i permitrootlogin
```

Expected modern output on hardened systems:
```text
permitrootlogin no
```

### Provision an Unprivileged Administrative Operative

Never manage systems without an attributed personal unprivileged user account:

```bash
# Create dedicated administrative user
sudo adduser sysadmin

# Append user to the sudoers group
sudo usermod -aG sudo sysadmin
```

Verify that the operative can authenticate with an unprivileged Ed25519 key pair:

```bash
# As the sysadmin operative, deploy the public key
mkdir -p ~/.ssh
chmod 700 ~/.ssh
nano ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

### Configure Modular SSH Drop-in Hardening

Modern Ubuntu and Debian distributions utilize `/etc/ssh/sshd_config.d/*.conf` drop-in directories for modular configuration management. Avoid editing the base `/etc/ssh/sshd_config` directly:

<CodeTabs tabs={[
  {
    filename: "/etc/ssh/sshd_config.d/99-hardened.conf",
    language: "apacheconf",
    content: `# Enterprise OpenSSH Daemon Hardening
# Disable direct root login entirely
PermitRootLogin no

# Enforce strict public-key cryptography
PasswordAuthentication no
PubkeyAuthentication yes
AuthenticationMethods publickey

# Session and Timeout Hardening
LoginGraceTime 30
MaxAuthTries 3
MaxSessions 2
ClientAliveInterval 300
ClientAliveCountMax 2

# Modern Cryptographic Ciphers & MACs
KexAlgorithms curve25519-sha256,curve25519-sha256@libssh.org
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com
MACs hmac-sha2-512-etm@openssh.com
`
  },
  {
    filename: "/etc/ssh/sshd_config.d/50-ansible-root-match.conf",
    language: "apacheconf",
    content: `# Optional: Scoped Root Access for Automation Bastion ONLY
# Keeps root login disabled globally, but permits key auth from trusted CIDR
Match Address 10.10.10.50/32
    PermitRootLogin prohibit-password
    AuthenticationMethods publickey
`
  }
]} />

### Pre-Flight Verification and Graceful Reload

Never restart the SSH daemon blindly without validating the configuration grammar first. If a syntax error exists, restarting will drop the daemon and permanently lock you out of the machine:

```bash
# 1. Run syntax validation check
sudo sshd -t

# 2. If exit code is 0 (no output), gracefully reload systemd unit
sudo systemctl reload ssh
```

<Callout type="tip" title="Always Maintain an Active Session">
Keep your current terminal session open in one window while opening a second terminal window to test logging in with your new user and SSH key: `ssh -i ~/.ssh/id_ed25519 sysadmin@server-ip`.
</Callout>

</Steps>

## Least-Privilege Sudoers Configuration

Once direct root SSH ingress is terminated, all administrative tasks require privilege escalation through `sudo`. Fine-grained control is configured inside `/etc/sudoers.d/`:

```bash
# Create a dedicated sudoers drop-in file
sudo visudo -f /etc/sudoers.d/99-sysadmin-policy
```

Append the desired policy:

```text
# Allow sysadmin to run all commands with password verification
sysadmin ALL=(ALL:ALL) ALL

# Optional: Require re-authentication every 10 minutes
Defaults:sysadmin timestamp_timeout=10
```

To audit every command executed via root privilege:

```bash
# Monitor privileged command execution in real-time
sudo journalctl -u sudo -f
```
