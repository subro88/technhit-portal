## Key Observability Takeaways

- **Zero-Overhead In-RAM Metrics**: Linux monitoring utilities do not query physical hardware directly; they read lightweight pseudo-files in `/proc` and `/sys` generated dynamically by the kernel with `< 0.1%` CPU overhead.
- **Interactive Multi-Core Profiling**: Modern TUIs like `btop` and `htop` provide real-time per-core CPU bars, process parentage trees, and instant signal dispatching (SIGTERM/SIGKILL).
- **Storage Bottleneck Pinpointing**: `iostat` measures block device queue saturation (`%util` and `await`), while `iotop` uncovers the exact process PID thrashing the disk.
- **Runqueue vs Memory Thrashing**: `vmstat` distinguishes CPU-bound spikes (`r`) from uninterruptible disk wait (`b`) and active memory swap thrashing (`si`/`so`).
- **File Descriptor Leaks**: `lsof +L1` pinpoints deleted log files still held open by un-restarted background services that silently consume disk space.

## Linux Kernel Telemetry & Performance Observation Pipeline

When an incident alert fires in production, guessing whether the issue is CPU starvation, memory leak, NVMe queue saturation, or TCP socket exhaustion wastes precious minutes.

<ArchitectureDiagram type="system-telemetry" title="Linux Kernel Telemetry Extraction & SRE Observation Architecture" />

<Callout type="benchmark" title="The Load Average Myth: What '18.0' Really Means">
A common misconception is that a high Linux load average always indicates excessive CPU consumption. In reality, Linux load average tracks the average number of threads in two distinct states: **Runnable (`R`)** (competing for CPU cores) and **Uninterruptible Sleep (`D`)** (waiting on I/O operations such as disk reads or network storage).

If your 4-core server shows a load average of `18.0` but `top` reports `92% idle CPU`, your processors are completely free—your server is paralyzed waiting for saturated storage controllers or stalled NFS mounts!
</Callout>

## Observability Virtual Filesystem Layout

Linux exposes kernel telemetry via virtual filesystems mounted in RAM:

<FileTree>
- /proc/
  - stat // Raw CPU time slices (user, nice, system, idle, iowait, steal)
  - meminfo (highlight) // Total, free, available, buffers, cached, dirty pages
  - diskstats (highlight) // Read/write sector counters and I/O wait ticks
  - loadavg // 1, 5, and 15-minute system load averages
  - [pid]/
    - status // Process memory footprint (VmRSS, VmSize)
    - fd/ // Active open file descriptors and socket handles
- /sys/
  - block/ // Physical storage device queue settings and scheduler profiles
  - devices/system/cpu/ // Per-core clock frequencies and power telemetry
</FileTree>

## The 5 Essential Linux Performance Tools

<Steps>
  <Step title="1. Interactive Process & Multi-Core Profiling: btop / htop">
    While legacy `top` is ubiquitous, modern production engineering relies on **`btop`** (or **`htop`**) for real-time visual inspection of per-core utilization, memory pressure, and process hierarchy.

    <TerminalBlock
      command="sudo apt install -y btop htop && btop"
      title="Launch btop Terminal Monitor"
      os="Debian 12 / Ubuntu 24.04"
    />

    <Callout type="tip" title="Key Interactive Shortcuts">
      - **F5 / t**: Toggle tree view to identify parent/child daemon forks.
      - **P**: Sort processes by CPU consumption.
      - **M**: Sort processes by Resident Memory (RSS).
      - **k / F9**: Send graceful termination signal (`SIGTERM` 15) to a runaway PID.
    </Callout>
  </Step>

  <Step title="2. Storage Throughput & Block Queue Saturation: iostat & iotop">
    When load spikes occur with low CPU percentage, verify storage subsystem latency using `iostat` from the `sysstat` package:

    <TerminalBlock
      command="sudo apt install -y sysstat iotop && iostat -xz 1 3"
      title="Sample Extended Disk Telemetry Every 1 Second"
      os="Linux"
    />

    Expected critical columns:
    - **`r_await` / `w_await`**: Average time (in milliseconds) for read/write requests to be served. Healthy NVMe SSDs should be `< 1.0 ms`; spinning disks should be `< 15.0 ms`.
    - **`%util`**: Device bandwidth saturation percentage. Consistently near `100%` indicates an I/O bottleneck.

    To discover exactly which process is causing the disk write storm, run `iotop`:

    <TerminalBlock
      command="sudo iotop -oP --iter=3"
      title="Trace High-I/O PIDs in Real Time"
      os="Linux"
    />
  </Step>

  <Step title="3. Virtual Memory & Runqueue Scheduler Audits: vmstat">
    `vmstat` provides instantaneous visibility into whether the operating system is CPU-bound, storage-bound, or experiencing active memory thrashing:

    <TerminalBlock
      command="vmstat 1 5"
      title="Run Continuous 1-Second Virtual Memory Sampling"
      os="Linux"
    />

    <Callout type="warning" title="Deciphering Critical vmstat Columns">
      - **`r` (runnable)**: Number of processes waiting for CPU time. If `r` consistently exceeds the number of physical CPU cores, your system is CPU-starved.
      - **`b` (blocked)**: Number of processes in uninterruptible sleep (usually waiting on disk I/O). High `b` confirms storage queue lockups.
      - **`si` / `so` (swap-in / swap-out)**: Memory pages swapped to/from disk per second. Having non-zero used swap is fine, but continuous non-zero `si`/`so` indicates active memory starvation and catastrophic thrashing!
    </Callout>
  </Step>

  <Step title="4. Socket & Open File Descriptor Analysis: ss & lsof">
    On modern Linux, **`ss`** replaces deprecated `netstat`. Because `ss` communicates directly with kernel Netlink sockets rather than scanning text files in `/proc/net`, it returns results instantaneously even on servers with 50,000+ active connections:

    <TerminalBlock
      command="ss -tulnp"
      title="Audit Listening TCP/UDP Sockets with Owning PIDs"
      os="Linux"
    />

    **Unlinked File Leak Detection**: When `df -h` shows `100% Full` but `du -sh /*` reports only 20GB used, an unlinked deleted log file is held open by a running service:

    <TerminalBlock
      command="sudo lsof +L1"
      title="Find Deleted Files Still Holding Disk Space"
      os="Linux"
    />

    Once the offending PID is identified (e.g. an un-restarted `nginx` or `app` daemon), restart that service to release the filesystem blocks immediately without rebooting.
  </Step>

  <Step title="5. Persistent Cluster Metrics: Prometheus node_exporter">
    Interactive terminal commands are ideal for live incident triage, but diagnosing intermittent latency spikes requires persistent historical time-series telemetry.

    Deploy `node_exporter` to expose kernel telemetry over HTTP:

    <TerminalBlock
      command="sudo apt install -y prometheus-node-exporter && sudo systemctl enable --now prometheus-node-exporter"
      title="Deploy Prometheus Node Exporter"
      os="Linux"
    />

    Verify the metrics stream:

    <TerminalBlock
      command="curl -s http://localhost:9100/metrics | grep -E '^node_cpu_seconds_total|^node_memory_MemAvailable' | head -n 4"
      title="Inspect Raw Prometheus Metric Stream"
      os="Linux"
    />
  </Step>
</Steps>

<Callout type="tip" title="Rapid 60-Second SRE Incident Triage Checklist">
When alerted to an emergency outage, run these four commands in order:
1. `uptime` (Check load average trend across 1, 5, 15 minutes)
2. `vmstat 1 3` (Verify `r` runqueue vs `b` I/O wait and `si`/`so` swap thrashing)
3. `iostat -xz 1 2` (Identify saturated storage drives `%util > 95%`)
4. `ss -s` (Check for TCP socket allocation exhaustion)
This 60-second sequence identifies whether the root cause is CPU, RAM, Disk, or Network.
</Callout>
